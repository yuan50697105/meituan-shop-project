# 05 · 支付与商家分账方案（核心）

> 版本：v1.0 ｜ 适用：单校 2–5 万学生，日订单峰值 3000–8000
> 本文是本项目**最重要的设计文档**。运营方是大学、核心痛点是商家分账，因此资金流与合规边界必须先于功能设计定稿。

---

## 0. 一页结论

1. **平台不碰钱**。采用「学校全资运营公司 + 微信支付服务商模式 + 特约商户逐户进件 + 服务商分账」。学生付款直接进入商家自己的特约商户号，微信（财付通）按平台指令直接清分，平台不设资金池。
2. **学校本部不收款、不分账、不开票**。签约、收佣、开票主体是校资产经营公司（独立法人）；学校后勤集团负责食安与商户考核。
3. **商户分五类处理**：自营、有照承包、无照档口、校外商户、配送方。禁止用一个「平台大商户号」收所有档口的钱——那是典型二清。
4. **结算只做 T+1 自动结算**。微信侧资金直达商户号并 T+1 到账；平台不做提现审批、不做资金池、不做代付。结算模块的职责是「分账执行 + 对账 + 报表 + 开票」。
5. **分账基数只能是用户实付金额**。平台补贴不得进入分账；当商家应收 + 配送费 + 佣金 > 用户实付时，差额由平台以「对公转账」月结补足，而不是靠分账「变出钱」。
6. **退款分两级**：分账前原路退回；分账后走微信「分账回退」，回退失败由平台先行垫付给用户，形成对商家的应收欠款，按月追偿。
7. **保证金不由平台保管**。改为食安责任险/银行保函，避免平台收保证金构成资金池。
8. **需要校方书面拍板的三件事**：运营主体、承包商户货款是否允许不进学校账户、无照档口的整改路径。这三件事未定，开发不应启动。

## 1. 合规前提

### 1.1 什么是「二清」

判断二清不看有没有分账系统，而看四个要件：

1. 收款主体是平台/学校，而不是实际销售商品的商户；
2. 资金进入平台/学校自有账户并形成沉淀（哪怕只停留一天）；
3. 平台自行决定结算时间、金额、对象；
4. 由平台向商户发起结算，而不是持牌机构直接清分。

「学校统一收款 + 月末批量转账」四条全中，是典型二清。依据《非银行支付机构监督管理条例》（国务院令第 768 号，2024-05-01 施行）第四十七条，可取缔、没收违法所得并处 50–200 万元罚款；情节严重可触及《刑法》第 225 条非法经营罪。同时叠加学校财经纪律问题（小金库、坐收坐支、公款私存）与税务问题（发票流与资金流不一致）。

### 1.2 合法边界

| 形态 | 销售方 | 资金流向 | 结论 |
|---|---|---|---|
| 自营 | 学校/后勤公司 | 学生 → 学校/公司商户号 | ✅ 合法 |
| 代理收单 | 各商户 | 学生 → 持牌机构 → 各商户 | ✅ 合法 |
| 代收代付 | 各商户 | 学生 → 学校账户 → 商户 | ❌ 二清 |

### 1.3 教育公益约束

教发〔2011〕7 号明确：学生食堂场地零租赁、免收管理费、学校不得以任何形式从学生食堂盈利。因此：

- 平台服务费**不能由学校以「管理费/进场费/资源占用费」名义向档口收取**；
- 必须由独立法人的运营公司以「信息技术服务费」收取，价格公允、非排他，并保留商户选择权；
- 建议只向商户收服务费，**不向学生收平台服务费**，避免触碰教育收费红线。

## 2. 总体资金流

```
学生（微信支付）
      │  支付订单金额 U
      ▼
特约商户号（收款主体 = 实际销售方）
      │  资金落在商户自己的商户号，平台不归集
      │  平台以服务商身份发起分账指令
      ├──► 配送方商户号        D（配送费）
      ├──► 运营公司商户号      C（平台技术服务费/佣金）
      └──► 商户留存            U - D - C（微信 T+1 自动结算到商户银行卡）

平台补贴 Δ（如有）
      └──► 运营公司对公账户 ──月结对公转账──► 商户/配送方（需发票）
```

**三条铁律：**

1. 任何情况下，分账总额不得超过该笔支付的实际到账金额；分账明细之和 ≤ U。
2. 平台与商户之间的资金往来只有两种：微信分账（平台从商户处分出佣金）、平台对公付款（补贴/赔付）。平台绝不代收商户货款。
3. 所有金额以「分」为单位用 `BIGINT` 存储，计算用 `BigDecimal`，最终 `HALF_UP` 到分。

## 3. 商户分层与进件

### 3.1 五类商户

| 类型 | 法律主体 | 收款方式 | 是否分账 | 说明 |
|---|---|---|---|---|
| A 自营食堂/档口 | 学校/后勤集团/全资餐饮公司 | 学校/公司特约商户号 | 不向档口分账，仅内部成本核算 | 学校是销售方，承担食安/税务/用工责任 |
| B 有照承包档口 | 承包方个体户/公司 | 承包方自己的特约商户号 | 是（向平台分佣金） | 首选路径，合同/执照/收款主体三者一致 |
| C 无照档口 | 暂无独立主体 | 先纳入 A 自营化，或限期办照转 B | 过渡期不分账 | 不得以「平台大商户」代收 |
| D 校外商户 | 独立法人/个体户 | 自有特约商户号 | 是 | 需学校准入与配送入校政策 |
| E 配送方 | 配送公司 | 配送公司商户号 | 是（收配送费） | 个人骑手由劳务公司代发，不直接作分账接收方 |

### 3.2 进件材料

- 营业执照/事业单位法人证书/个体户执照；
- 法人身份证、结算银行卡/对公账户；
- 食品经营许可证（餐饮类目必备）；
- 门店照片、经营场所证明；
- 微信支付特约商户进件资料，并**在进件时签约分账权限**（补签成本高）。

### 3.3 无照档口的现实路径

按可行性排序：

1. **纳入学校持照餐饮公司自营化**（最稳，但学校承担食安/税务/用工责任）；
2. 引导办理个体工商户（校园场地常无法作为注册地址，落地率低）；
3. 限期整改，未完成则下线（必须提前告知，避免商户抵触）。

> 不要设计「无照档口挂靠平台商户号收款、平台再转给档口」——这就是二清。

## 4. 分账规则与金额口径

### 4.1 金额定义（先把公式定死）

| 符号 | 含义 |
|---|---|
| `G` | 商品原价合计 |
| `Pk` | 打包费 |
| `D` | 配送费（用户应付） |
| `DiscM` | 商家承担的优惠（商家券、商家满减） |
| `DiscP` | 平台承担的优惠（平台券、新客立减） |
| `U` | 用户实付 = `G + Pk + D - DiscM - DiscP` |
| `M` | 商家应收 = `G - DiscM + Pk` |
| `C` | 平台佣金 = `(G - DiscM) × 佣金率` |
| `Δ` | 平台补贴应付 = `M + D + C - U` = `DiscP`（恒等） |

> 关键结论：`Δ` 就是平台承担的优惠。它**不能进入微信分账**，只能由平台对公补付。

### 4.2 分账明细

一次分账只产生两类明细：

- 配送方：`D`
- 平台：`C`
- 商户留存：`U - D - C`

约束：

- `D + C ≤ 30% × U`（微信分账默认上限，需签约时确认；可申请提额）
- 若不满足，通过**起送价**兜底：`起送价 ≥ (D + C) / 30%`
  - 例：配送费 2 元、佣金率 5%，则起送价 ≥ 2 / 0.25 = 8 元，建议设 10 元。
- 分账总额不得超过 `U`；分账执行前做资金校验，不通过则转人工。

### 4.3 佣金与费率

| 商户类型 | 平台佣金率 | 备注 |
|---|---|---|
| 自营 | 0 | 内部核算，不计佣金 |
| 校内承包档口 | 5%（3%–8% 可配） | 以技术服务费名义 |
| 校内商铺 | 5% | |
| 校外商户 | 6% | 含平台流量与配送协调 |
| 配送方 | 0（收 100% 配送费） | 平台不抽配送费 |

费率按商户维度配置，**版本化**：订单支付时冻结 `split_rule_snapshot`，历史订单只读快照，改费率不影响历史账。

### 4.4 分账触发时点

- 订单送达并确认收货（或自动确认）后，进入售后期；
- 售后期默认 **2 小时**（餐饮），可配置 0–24 小时；
- 售后期结束后的 **T+1 02:00** 批量执行分账；
- 商户留存部分由微信 T+1 自动结算至商户银行卡。

> 这样既满足「T+1 自动结算」，又给餐饮售后留出处理窗口。若校方坚持严格 T+1（送达次日），把售后期设为 0 即可，配置化解决。

## 5. 退款、售后与欠款

### 5.1 分账前退款

- 全额/部分退款均原路退回，微信退款成功率接近 100%；
- 退款金额不得超过剩余可退金额；
- 同一订单的退款幂等键：`refundNo`。

### 5.2 分账后退款

- 调用微信「分账回退」，按各接收方实际分账金额比例回退；
- 平台佣金优先全额回退（平台不赚退款订单的钱）；
- 回退失败（接收方余额不足、账户异常）→ 状态记为 `PART_REVERSED`，差额进入 `arrears`（欠款台账）；
- **用户侧始终由平台先行垫付全额退款**，不得让用户承担回退失败；
- 欠款通过商户后续佣金抵扣（需商户书面授权）或月度对公追偿；
- 单商户垫付上限默认 2000 元，超限转人工审批。

### 5.3 保证金

**平台不收取、不保管保证金。** 替代方案：

1. 要求商户购买食品安全责任险（推荐）；
2. 银行保函；
3. 学校财务代管（流程长，仅对高风险商户）。

> 平台收保证金并保管会形成资金池，与「平台不碰钱」直接冲突。

### 5.4 赔付标准（可配置）

| 场景 | 赔付 | 承担方 |
|---|---|---|
| 超时送达 | 配送费 30%–100% | 配送方 |
| 少送/错送 | 商品实付金额 | 商家 |
| 食品安全投诉 | 实付金额 + 医疗凭证 | 商家/食安险 |
| 平台系统故障 | 实付金额 | 平台 |

## 6. 优惠与补贴

### 6.1 出资方矩阵

| 优惠类型 | 出资方 | 对分账的影响 |
|---|---|---|
| 商家券/商家满减 | 商家 | 降低 `M` 和 `U`，分账不变 |
| 平台券/新客立减 | 平台 | 降低 `U`，`M` 不变 → 产生 `Δ`，平台对公补付 |
| 配送费减免 | 平台或商家 | 若平台出，`Δ` 增加；若商家出，`D` 降低 |
| 平台配送补贴 | 平台 | 直接补配送方，走 `Δ` |

### 6.2 记账原则

- 佣金收入**全额确认**，平台补贴作为营销费用列支，不做净额抵扣（避免少计收入与虚开发票风险）；
- 每一笔优惠、每一个出资方生成一条 `fund_allocation` 明细，禁止只存总额；
- 平台补贴现金部分设月度预算上限，超出需审批。

### 6.3 平台补贴支付

- 按日汇总、按月对公转账；
- 商户需向运营公司开具「营销服务费」发票，或按税务师意见以销售折让处理；
- 首期可把补贴控制在「佣金可覆盖」范围内，减少对外付款流程。

## 7. 对账体系

### 7.1 四层对账

| 层级 | 比对对象 | 频率 | 责任 |
|---|---|---|---|
| 支付对账 | 微信支付账单 vs `pay_order` | 日 | 技术 + 财务 |
| 退款对账 | 微信退款账单 vs `refund_order` | 日 | 技术 + 财务 |
| 分账对账 | 微信分账单 vs `split_order/detail` | 日 | 技术 + 财务 |
| 结算对账 | 商户银行到账 vs 结算凭证 | 日/月 | 财务 |

### 7.2 恒等式

```
用户实付 U
  = 商户留存 (U - D - C)
  + 配送分账 D
  + 平台佣金 C

商家应收 M
  = 商户留存 (U - D - C)
  + 平台补贴 Δ

其中 Δ = DiscP（平台承担优惠）
```

通道费单独建模为 `channel_fee`，不进入分账公式，但必须进入对账恒等式：

```
商户银行到账 = 商户留存 - 通道费
```

### 7.3 差异处理

- 容差：单笔 0.01 元、日累计 1 元，自动轧差；
- 超容差生成差异工单，T+3 闭环；
- 每日输出《资金对账日报》，每月末做账户全量重算（`SUM(流水) = 余额`）；
- 对账数据保留 10 年，个人信息去标识化分层保存。

## 8. 发票与税务

| 场景 | 开票方 | 受票方 | 税率/票据 |
|---|---|---|---|
| 学生购买餐品 | 商户 | 学生 | 商户按餐饮服务开票 |
| 平台技术服务费 | 运营公司 | 商户 | 6% 增值税专用/普通发票 |
| 配送费 | 配送公司 | 商户/平台（按合同） | 6% 或 9% |
| 平台补贴 | 商户 | 运营公司 | 营销服务费发票或销售折让 |
| 学校自营部分 | 学校/后勤公司 | 学生 | 按事业单位票据规定 |

> 三流一致（合同流、资金流、发票流）必须在合同中写死；补贴与退款的红冲时点需税务师书面意见。

**约束：**

- 所有金额 `BIGINT`（分）；
- `fund_fund_flow` 只插入，不更新、不删除；冲正用反向流水；
- 账户扣减用条件更新：`UPDATE ... SET balance = balance - ? WHERE balance >= ?`；
- 余额绝不以 Redis 为准，Redis 只做幂等键与限流。

## 10. 状态机

### 10.1 支付单

```
INIT → PAYING → PAID → REFUNDING → REFUNDED
                  │          └──→ PART_REFUNDED
                  └──→ CLOSED（超时未支付）
```

### 10.2 分账单

```
PENDING → SPLITTING → SUCCESS
                    ├──→ PART_SUCCESS
                    └──→ FAILED → (重试) → SPLITTING
SUCCESS/PART_SUCCESS → REVERSING → REVERSED / PART_REVERSED
```

> 回退失败必须落 `PART_REVERSED` 并生成欠款，**禁止回写 SUCCESS**。

### 10.3 结算凭证

```
GENERATED → CONFIRMED（微信自动结算，平台仅确认凭证）
```

> 微信通道下平台不发起打款；只有银行存管/对公转账通道才有 `PAYING → PAID`。

### 10.4 退款单

```
INIT → PROCESSING → SUCCESS / PART_SUCCESS / FAILED
```

## 11. 核心接口

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/fund/pay-orders` | 创建支付单，返回微信支付参数 |
| POST | `/api/fund/callback/wechat/pay` | 支付回调（验签 + 幂等） |
| GET | `/api/fund/pay-orders/{orderNo}` | 查询支付状态（主动查单兜底） |
| POST | `/api/fund/refunds` | 发起退款 |
| POST | `/api/fund/callback/wechat/refund` | 退款回调 |

## 12. 技术实现要点

1. **模块化单体**：`fund-center` 作为独立 Maven 模块，独立包、独立表前缀、独立权限；首期不拆微服务。
2. **回调处理**：验签 → 幂等 CAS（`wx_transaction_id` 唯一索引）→ 同事务写 outbox → 异步更新业务状态。
3. **主动查单**：支付/退款/分账都必须有定时查单兜底，不能只依赖回调。
4. **重试与补偿**：outbox 表 + 定时任务；指数退避；失败进死信表并告警。
5. **限流**：批量分账分批执行（每批 50–100 笔），错峰到 02:00–04:00，避免撞微信 API 限流。
6. **并发门禁**：退款与分账互斥（同一订单加分布式锁 + 状态门禁），防止「既分账又退款」。
7. **无重型中间件**：首期 MySQL + Redis + Spring Scheduler 足够；不引入 Doris/ClickHouse/WORM/KMS/三员分立。
8. **分区与归档**：流水表按月分区，保留 3 年在线、10 年归档。
9. **监控告警**：支付成功率、分账成功率、对账差异数、回退失败数、补贴应付余额。

## 15. 与常见错误设计的对照

| 错误设计 | 后果 | 本文修正 |
|---|---|---|
| 学校统一收款再分给商户 | 二清、财经纪律、税务三线风险 | 特约商户直收 + 服务商分账 |
| 平台补贴计入分账 | 分账总额 > 实付，必然失败/透支 | 补贴走对公月结，分账基数只用 `U` |
| T+7/月结/保证金抵扣 | 微信分账不支持平台控账期 | 只做 T+1，保证金改保险/保函 |
| 平台收保证金保管 | 形成资金池 | 食安险/银行保函 |
| 回退失败回写成功 | 掩盖欠款，对账丢失 | `PART_REVERSED` + 欠款台账 |
| 结算单既当凭证又当打款指令 | 重复付款 | 区分「凭证型」与「指令型」 |
| 无照档口挂靠平台商户号 | 二清 | 自营化或办照，禁止挂靠 |
| 全量双人复核 + 四级审批 | 退款积压 | 按金额与风险分级 |
