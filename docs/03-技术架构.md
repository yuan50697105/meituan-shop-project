# 03 · 技术架构

> 版本：v1.0 ｜ 规模基线见 [00](00-术语与口径.md) 第 6 节。

---

## 0. 结论先行

1. **模块化单体**，不是微服务。单校峰值下单 TPS < 10、查询 < 300，微服务的弹性收益为零，复杂度成本极高。用 Maven 多模块 + 包边界 + ArchUnit 守住模块化，未来可拆。
2. **首期中间件只有 MySQL 8 + Redis 7 + 对象存储 + Spring Scheduler + Outbox**。不引入 RocketMQ/XXL-Job/Sentinel/SkyWalking/Elasticsearch；到 M3 再按需引入。
3. **防超卖以数据库条件更新为唯一真相**，Redis 只做缓存/锁/限流/GEO；不做 Lua 预扣（除非秒杀）。
4. **骑手端必须是 App**（uni-app 打包），小程序无法后台定位保活与厂商推送。
5. **支付资金域独立模块** `ms-fund`，独立表前缀、独立权限、独立审计；详见 [05](05-支付与分账方案.md)。
6. **单机 Docker Compose 起步**（16C32G），Nginx 前置，应用无状态可横向扩展；阶段 2 再上主从/集群。

## 1. 规模与目标

| 指标 | 值 | 设计目标 |
|---|---|---|
| 日订单 | 稳态 2500，峰值 6000，设计 8000 | 峰值下单 TPS < 10 |
| 查询 QPS | 峰值 < 300 | P99 < 300ms |
| 用户 | 3 万注册，1.5 万 MAU | 登录/查询可缓存 |
| 商家 | 120–180 | 单表无压力 |
| 骑手 | 60–120 | 定位 10s/次，Redis GEO |
| 可用性 | 99.9%（首期） | 单机故障 < 30 分钟恢复 |
| 数据量 | 年 200–300 万订单 | 5 年约 1500 万订单，单表可承受 |

> 结论：**不需要分库分表**。订单、流水类表按月分区 + 归档即可。

## 3. 后端模块划分

| 模块 | 职责 | 依赖 |
|---|---|---|
| `ms-common` | 统一响应、异常、工具、雪花 ID、金额、审计、幂等 | 无 |
| `ms-user` | 用户、学生认证、地址、信用分、角色权限 | common |
| `ms-campus` | 校区、园区、楼栋、配送点、自提柜、校历、配送定价 | common |
| `ms-merchant` | 商家、门店/档口、资质、合同、营业时间、结算账户 | common, campus |
| `ms-product` | 类目、SPU/SKU、规格、库存、库存流水 | common, merchant |
| `ms-order` | 购物车、订单、订单明细、状态流水、售后 | common, product, merchant, campus |
| `ms-fund` | 支付、退款、分账、结算、对账、欠款、发票 | common, order |
| `ms-delivery` | 骑手、认证、排班、配送单、轨迹、收入、异常 | common, order, campus |
| `ms-marketing` | 券、满减、活动、会员、积分、拼单、团购、广告 | common, order |
| `ms-review` | 评价、标签、回复、投诉 | common, order |
| `ms-errand` | 跑腿订单、计价、接单 | common, delivery |
| `ms-notify` | 站内信、订阅消息、短信、推送模板 | common |
| `ms-admin` | 后台聚合查询、审核、报表、配置 | 所有模块的 api |
| `campus-app` | 启动类、配置、Flyway、OpenAPI | 所有模块 |

### 3.1 模块边界规则

- 跨模块只允许调用对方 `api` 包的接口，**禁止直接查对方表**；
- 跨模块写操作通过领域事件 + Outbox 最终一致；
- 用 ArchUnit 在 CI 中强制：`ms-order` 不得 import `ms-fund` 的 mapper；
- 每个模块独立 `mapper`/`service`/`api`/`event` 包。

### 3.2 部署形态

- 首期：**一个应用进程**，按 URL 前缀区分 `app-api` / `merchant-api` / `rider-api` / `admin-api`；
- 阶段 2：若管理后台查询压力大，可把 `admin-api` 拆为独立进程（共享库）；
- 不建议按端拆 BFF 服务，增加调用链与部署复杂度。

## 4. 中间件选型（明确取舍）

| 能力 | 首期方案 | 何时升级 | 理由 |
|---|---|---|---|
| 消息队列 | **Outbox 表 + Spring Scheduler 轮询** | M3 后订单事件量增大再引入 RocketMQ 5 | 首期 TPS < 10，MQ 是过度设计 |
| 延迟任务 | **Redis ZSet + 定时扫描**（订单 15 分钟关闭） | 量增大后用 RocketMQ 延迟消息 | 简单可靠，避免额外组件 |
| 定时任务 | **Spring Scheduler + ShedLock**（多实例防重） | M5 后引入 XXL-Job | 首期任务 < 20 个 |
| 缓存/锁 | Redis 7（Redisson） | 集群模式 | 一栈承担缓存、锁、验证码、GEO、限流 |
| 搜索 | MySQL 前缀/全文 + 应用层排序 | 商品数 > 5 万或需要多因子排序时引入 ES | 首期 120–180 商家，MySQL 足够 |
| 对象存储 | MinIO（自建）或阿里云 OSS | 按量增长 | 证照/商品图/小票 |
| 监控 | Spring Actuator + Micrometer + Prometheus + Grafana | 需要链路追踪时加 Tempo/Jaeger | 不上 SkyWalking |
| 日志 | JSON 结构化日志 + Loki（可选） | — | 先保证 traceId 贯穿 |
| 配置 | Spring Config + 数据库配置表 | 多环境复杂后引入 Nacos | 首期不引入注册中心 |

> **反过度设计清单：** 不引入 Spring Cloud、Nacos、Sentinel、SkyWalking、Elasticsearch、Doris/ClickHouse、KMS、WORM、三员分立。支付模块的审计与不可变流水用应用层 + 数据库约束实现即可。

## 5. uni-app 多端工程

### 5.1 仓库结构

```
frontend/
├── pnpm-workspace.yaml
├── packages/
│   ├── shared/          # 类型、请求封装、常量、工具、状态字典
│   └── ui/              # 跨端组件（按钮/空态/加载/弹窗）
├── apps/
│   ├── student/         # 学生端（微信小程序 + H5）
│   ├── merchant/        # 商家端（微信小程序 + H5）
│   ├── rider/           # 骑手端（App 为主 + 小程序查询）
│   └── admin/           # 管理后台（Vue3 + Element Plus，独立 Vite）
└── package.json
```

### 5.2 关键约束

- **主包 ≤ 1.5MB**；按业务分包（order、marketing、user、errand），配置预下载；
- 跨端差异全部收敛到 `packages/shared/platform`（登录、支付、定位、推送、存储）；
- 请求封装统一：拦截器注入 JWT、traceId、错误码处理、重试；
- 状态管理 Pinia；按端拆 store；
- 环境配置：`.env.development` / `.env.staging` / `.env.production`；
- 小程序隐私协议、订阅消息模板、支付目录需提前配置。

### 5.3 骑手 App 专项

- 后台定位：App 端使用 uni-app 原生定位插件 + 保活策略；Android 前台服务 + 厂商推送；
- 弱网：订单与状态本地缓存，恢复后按 `updated_at` 增量同步；
- 电量：定位 10 秒/次，静止时降频到 30 秒；
- 这是本项目**最大的客户端技术风险**，需在 M1 做技术验证。

## 6. 认证与鉴权

| 项 | 方案 |
|---|---|
| 登录 | 微信 code2session（学生/商家/骑手）；后台账号密码 + 图形验证码 |
| Token | JWT Access（2h）+ Refresh（30d）；Refresh 存 Redis 白名单，可强制下线 |
| 权限 | Spring Security + RBAC；角色：STUDENT / MERCHANT / RIDER / OPERATOR / FINANCE / ADMIN |
| 数据范围 | ALL / CAMPUS / SHOP / SELF；DAO 层强制注入 `campus_id`/`merchant_id`/`user_id` 条件 |
| 水平越权 | 所有资源归属服务端校验，禁止只靠前端隐藏 |
| 高危操作 | 独立权限点 + 双人复核 + 审计日志（退款 >500、费率变更、分账重试） |
| 虚拟号 | 用户/骑手/商家联系使用虚拟号，保护隐私 |
| 后台安全 | 强制 HTTPS、密码策略、登录失败锁定、可选 IP 白名单、CSRF Token |

## 7. 并发、一致性与幂等

### 7.1 库存

- 表 `p_stock`：`stock`、`locked_stock`、`sold_count`；
- 下单锁定：`UPDATE p_stock SET locked_stock = locked_stock + ? WHERE sku_id = ? AND stock - locked_stock >= ?`；
- 支付成功：`locked_stock -= ?; sold_count += ?`；
- 取消/超时：`locked_stock -= ?`；
- **数据库条件更新是唯一真相**；Redis 只做展示缓存；
- 每日库存对账：用 `p_stock_log` 重算并修正泄漏。

### 7.2 订单幂等（四层）

1. 客户端 `submitToken`（Redis SETNX，5 分钟）；
2. 请求头 `X-Request-Id` 幂等表；
3. 数据库唯一索引（`user_id + submit_token`）；
4. 状态机 CAS。

### 7.3 支付幂等

- `fund_pay_order` 唯一索引 `(channel, wx_transaction_id)`；
- 回调验签 → 幂等表 CAS → 同事务写 outbox → 返回成功；
- 重复回调直接返回成功，不重复更新。

### 7.4 跨域一致性

- 订单支付成功 → 写 `sys_outbox` → 定时投递 → 更新订单/库存/通知；
- 消费方幂等（事件 ID 唯一索引）；
- 失败重试 3 次 → 死信表 → 告警 → 人工；
- 每日对账扫描悬挂单（已支付未接单、已送达未完成）。

### 7.5 分布式锁

- Redisson；锁粒度：订单号、支付单号、分账单号；
- 退款与分账互斥：同一订单加锁 + 状态门禁；
- 锁超时 10 秒，看门狗续期；禁止用 Redis 锁替代数据库唯一约束。

## 9. 安全与合规

- 全站 HTTPS；敏感字段 AES-GCM 加密（手机号、身份证、银行卡）；
- 日志脱敏（手机号中间 4 位、身份证、地址）；
- 文件上传：类型/大小校验、图片重新编码、私有桶 + 签名 URL；
- 限流：Redis + Bucket4j，按 IP/用户/接口；
- 防刷：验证码、设备指纹、同设备多账号限制、风控规则表；
- SQL 注入：MyBatis 参数绑定，禁止字符串拼接；
- XSS/CSRF：输出转义、后台 CSRF Token；
- 等保 2.0：首期二级备案，支付/用户模块按三级要求加固；P2 做三级测评与密评；
- 个人信息保护：最小必要、单独同意、可撤回、数据导出/删除；
- 审计：所有高危操作写 `sys_operation_log`，保留 3 年。

## 11. 关键取舍与风险

| 取舍 | 决定 | 理由 |
|---|---|---|
| 单体 vs 微服务 | 单体 | 规模小、团队小、运维成本低 |
| MQ | 首期不用 | Outbox + 定时任务足够 |
| 搜索引擎 | 首期 MySQL | 商家/商品量小 |
| 分库分表 | 不做 | 5 年 1500 万订单，单表可承受 |
| 骑手端载体 | App | 后台定位与推送 |
| 管理后台 | 独立 Vue3 Web | 不塞进小程序 |

| 风险 | 应对 |
|---|---|
| 单体腐化 | ArchUnit + 模块边界评审 + 禁止跨模块查表 |
| 单机单点 | 备份、降级开关、快速恢复演练；阶段 2 集群化 |
| 骑手 App 保活/推送 | M1 技术验证；备选第三方定位 SDK + 厂商推送 |
| 微信支付分账规则变化 | 抽象 `ChannelAdapter`；保留银行存管备选 |
| 外部接口不稳定（教务/一卡通/地图） | 超时、降级、人工兜底、缓存 |
| 小程序审核/类目 | 资质先行；H5 兜底 |
